# new-problem

Create `problems/<snake_case_title>/` so it is indistinguishable from the existing folders
(`two_sum`, `merge_sorted_array`, `evaluate_division`, ...), using the Python and C++ code and the
sample tests that **the user provides**.

## Golden rules

1. **Never invent data.** Number, title, difficulty, tags, complexities, code and tests all come
   from the user. If something is missing, ask. Do not guess "obvious" values (e.g. complexity), and
   do not write your own solution unless the user explicitly asks you to.
2. **Zero unnecessary back-and-forth.**
   - If the user provides information in their prompt (e.g., number, title, difficulty, tags, code, tests, complexity), **skip asking for it**.
   - If information is missing, ask for **all missing pieces in a single batch message**. Never ask one by one across multiple turns.
   - **No confirmation gates**: When all necessary information is present, do not pause to ask "Create it?" or "Ready to proceed?". Proceed directly to creating the files and verifying them.
   - **No gratuitous clarification questions**: If the code is deterministic, function names match, and sample outputs are clear, do not ask how to compare or whether to add edge cases. Use sensible defaults and verify by running tests.
3. **Don't change the user's algorithm.** Only make mechanical adaptations (see "Adapting the code")
   and tell the user exactly what you changed.
4. **Don't touch `README.md` by hand.** It is generated by `make readme`.
5. **Test cases are collected once and shared.** The user gives the sample tests a single time, in
   any readable format. The Python and C++ test files are both generated from that one list: same
   cases, same order, same count, same values. Never ask for them per language.
6. **`class Solution` is prohibited.** No generated file (`.py`, `.h`, `.cc`, tests) may contain a
   `Solution` class/struct or any wrapper class. Solutions are always free functions. If the pasted
   code is wrapped in `class Solution`, unwrap it automatically; never keep it and never ask whether to keep it.
7. **Git conventions (when requested):**
   - Branch naming: `feat-<number>-<PascalCaseTitle>` (e.g. `feat-27-Remove-Element`, `feat-88-Merge-Sorted-Array`).
   - Files to stage: `README.md` and `problems/<snake_case_title>/` (plus any shared utilities in `common/` if added).
   - Commit message: `feat: solve <number>. <Title> with unit testing`.
   - Push: `git push -u origin <branch_name>`.

## Step 0 - Read the current state (silently)

- `config/difficulties.yml` and `config/tags.yml` are the **only** valid values; read them silently.
- `ls problems/` to detect an existing folder with the same name or LeetCode number.
- If `problems/<snake>/` already exists, stop and ask the user how they wish to proceed.

## Step 1 - Collect missing information (in ONE single turn)

If the user pasted everything (or parts) in their message, extract:
- LeetCode number (e.g. `27`)
- Title (e.g. `Remove Element`)
- Difficulty (`easy`, `medium`, `hard` matching `config/difficulties.yml`)
- Tag(s) (matching `config/tags.yml`, e.g. `["Two Pointers"]`)
- Python solution
- C++ solution
- Sample test cases
- Time and space complexity (e.g. `O(n)`, `O(1)`)

If any of these are missing, ask for **all missing fields at once** in a single structured message:
```text
Please provide the following missing details to scaffold the problem:
- LeetCode Number & Title
- Difficulty (easy / medium / hard)
- Tag(s) (e.g. Two Pointers, Arrays & Hashing, etc.)
- Python solution
- C++ solution
- Sample test cases (inputs and expected outputs)
- Time & Space complexity
```
Do not split this into multiple rounds of questions.

## Step 2 - Derive silently

Do NOT pause to ask the user to confirm derived values. Derive silently:
- `slug` = title lower-cased, spaces to `-` -> URL `https://leetcode.com/problems/<slug>/`
- `snake` = title lower-cased, non-alphanumerics removed, spaces to `_` (folder and file prefix),
  e.g. `Remove Element` -> `remove_element`. Digits stay (`3Sum` -> `3sum`).
- `Pascal` = PascalCase title for C++ test types, e.g. `RemoveElement`.
- `function_name` = extracted from user's code (e.g. `removeElement`). If both Python and C++ use the same name, use it without asking.
- Data structures: If `TreeNode`, use `from common import TreeNode` and `#include "../../common/trees/treenode.h"`. If standard types (`int`, `vector`, `string`, `list`, etc.), no extra setup is needed.

## Step 3 - Test cases & Parity

Build one language-neutral list of cases:
`name`, one value per parameter, `expected`. Then generate both `<snake>_test.py` and `<snake>_test.cc` from that same list:
- Identical cases, identical order, identical number of cases, identical values.
- One name per case, written `snake_case` for Python `ids` and `PascalCase` for C++ `test_name` (`basic_example_1` <-> `BasicExample1`).
- The Python trailing `# comment` of each case is a short description.

**Handling edge cases and comparison without back-and-forth:**
- Use the user's provided sample tests. You may add common, verified edge cases (e.g. empty input, single element) if they pass against the user's solution, but **never pause to ask** the user "Do you want me to add extra edge cases?".
- For in-place array problems returning length `k`: assert `k == expected_k` and `nums[:k] == expected_nums`. Verify determinism against the user's code first. Do not pause to ask how to compare unless the test fails.

## Step 4 - Create the 7 files immediately

Do not show a plan and wait for "Create it" confirmation. Immediately create:

```
problems/<snake>/
├── BUILD.bazel
├── config.yml
├── <snake>.py
├── <snake>_test.py
├── <snake>.h
├── <snake>.cc
└── <snake>_test.cc
```

### `<snake>.py`

The project targets Python 3.14.8 (`.python-version`, `pyproject.toml`, CI); don't downgrade syntax.
A **free function** (never `class Solution`, no `self`), modern type hints (`list[int]`, `X | None`),
no `from typing import ...` for builtins.

```python
def merge(nums1: list[int], m: int, nums2: list[int], n: int) -> None:
    ...
```

### `<snake>_test.py`

```python
"""Test cases for the merge function."""

import pytest
from merge_sorted_array import merge


@pytest.mark.parametrize(
    "nums1, m, nums2, n, expected",
    [
        ([1, 2, 3, 0, 0, 0], 3, [2, 5, 6], 3, [1, 2, 2, 3, 5, 6]),  # Basic case
        ([], 0, [], 0, []),  # Empty arrays
    ],
    ids=[
        "basic_case",
        "both_empty",
    ],
)
def test_merge(nums1, m, nums2, n, expected):
    merge(nums1, m, nums2, n)
    assert nums1 == expected
```

### `<snake>_test.cc`

GoogleTest value-parameterised tests with C++20 designated initialisers:

```cpp
#include "merge_sorted_array.h"

#include <gtest/gtest.h>
#include <string>
#include <vector>

struct MergeSortedArrayCase {
    std::string test_name;
    std::vector<int> nums1;
    int m;
    std::vector<int> nums2;
    int n;
    std::vector<int> expected;
};

using MergeSortedArrayTest = ::testing::TestWithParam<MergeSortedArrayCase>;

TEST_P(MergeSortedArrayTest, TestCases) {
    MergeSortedArrayCase testCase = GetParam();
    merge(testCase.nums1, testCase.m, testCase.nums2, testCase.n);
    EXPECT_EQ(testCase.nums1, testCase.expected);
}

INSTANTIATE_TEST_SUITE_P(
    MergeSortedArrayTestCases, MergeSortedArrayTest,
    ::testing::Values(
        MergeSortedArrayCase{.test_name = "BasicExample",
                             .nums1 = {1, 2, 3, 0, 0, 0},
                             .m = 3,
                             .nums2 = {2, 5, 6},
                             .n = 3,
                             .expected = {1, 2, 2, 3, 5, 6}}),
    [](const ::testing::TestParamInfo<MergeSortedArrayCase> &info) { return info.param.test_name; });
```

## Adapting the code (mechanical changes only)

- **Always** remove `class Solution:` / `class Solution { public: ... };` and `self`, de-indent, and
  make it a free function. Helper methods become free functions (Python: nested or module-level; C++:
  anonymous namespace in `.cc`).
- Add missing `#include`s, move the signature to `.h`.
- Python: replace `typing.List[int]` by `list[int]`, `Optional[X]` by `X | None`.
- C++: use `std::size_t` for indexing where appropriate to avoid signed/unsigned comparison warnings under `-Wall -Wextra -Wpedantic`.
- Keep the LeetCode function name unchanged.

## Step 5 - Verify

Run from the repo root (activate `.venv` first if present: `source .venv/bin/activate`):

```bash
source .venv/bin/activate
make test-py:<kebab>      # e.g. make test-py:remove-element   (kebab = snake with - instead of _)
make test-cpp:<kebab>
PATH="/Library/Developer/CommandLineTools/usr/bin:$PATH" make format  # ensures clang-format and ruff run
make lint
make readme               # regenerates the README table from every config.yml
make update-badges        # refreshes the solution-count badges
make clean                # cleans test runners and dSYM files
git diff --exit-code problems/<snake>/  # CRITICAL: CI checks formatting with git diff; must have 0 diff!
git status
```

Rules:
- Check test parity: `<snake>_test.py` (`ids`) count equals `<snake>_test.cc` (`.test_name`) count.
- **CI format check compliance**: GitHub Actions runs `make format-cpp` and fails if `git diff --exit-code` is non-zero (`.github/workflows/linter-cpp.yml`). On macOS, `clang-format` is located at `/Library/Developer/CommandLineTools/usr/bin/clang-format`. Always ensure `clang-format` runs on all C++ files and any formatting changes are staged before committing.
- Check `git diff README.md`: only the new problem row and badge counts should change.
